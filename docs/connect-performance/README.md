# SmiRing Connect パフォーマンス改善の記録

2026-10-11 から始めた「一部のメンバーだけ Connect が使えないほど重い」問題への取り組みを、計測した数字つきでまとめたもの。
新しい計測をしたら、該当する節に追記していく。

- 対象の症状: 特定のPC（約5人）で、声が10秒遅れる・画面が固まる・操作できない。同じ人が Zoom / Meet では問題なし。
- 優先順位（決定事項）: **音声は絶対に途切れさせない ＞ 画面共有をきれいに保つ ＞ カメラ**
- 判断の原則（決定事項）: 端末のスペックではなく**実測した負荷**で判断する。背景エフェクトは自動でOFFにしない（下限は「標準」）。切り抜きの回数はカメラのコマ数の半分未満にしない。

---

## 0. 計測の道具

| 道具 | 使い方 | 中身 |
|---|---|---|
| 通話の診断 | 通話中「その他 > 通話の診断」→ 診断IDを共有 → `cd backend && npx tsx src/scripts/connectDiagnostics.ts get <ID>` | 送受信の詳細、ノイズキャンセルの遅れ、画面スレッドの停止など |
| 自動記録（テレメトリ） | 全員・全通話で自動。`npx tsx src/scripts/connectTelemetry.ts summary <UTCの日付>` | 2秒ごとの負荷・判断・回線・送信・レベラー・受信・Reactの描き直し |
| `/dev/blur-lab` | 公開ページ。誰でも開ける | 背景エフェクトの設定ごとの重さ |
| `/dev/share-lab` | 公開ページ。サーバー不要 | 画面共有の設定ごとの圧縮・デコードの重さ、ビットレート |
| `/dev/temporal-lab` | ログインが必要 | 受信側でコマ数を減らしたときのデコードの変化 |

## 1. 改善前の状態（基準）

**2019年 MacBook Air（Intel i5 2コア / Intel UHD 617 / Chrome 154）、2026-10-13、約15分の通話の診断**

| 項目 | 数値 | 意味 |
|---|---|---|
| ノイズキャンセル 1回分(64ms)の処理時間 | 平均 **99ms**、最大 418ms | 64ms以内に終わらないと遅れが積み上がる |
| ノイズキャンセルの待ち行列 | 最大 **14.6秒** | 「声が10秒遅れる」の正体 |
| 再生の途切れ | 15分で **78回** | 声のブツ切れ |
| カメラの圧縮がCPU不足で制限された割合 | **68%** のサンプル | VP8のソフトウェア圧縮が追いつかない |
| 画面スレッドの最長停止 | **7.2秒**（タイマーの遅れ最大 8.7秒） | 背景エフェクトのモデル読み込みで画面が固まる |
| 背景エフェクトの初回推論（高精細） | **4.3秒** | 同上 |
| 背景エフェクトの画質 | 標準→高精細→標準を自動で往復 | 「余裕がある」と判断して自動で上げ、すぐ重くなって下げていた |

原因（確定）:
1. ノイズキャンセル（GTCRN）の待ち行列に上限がなく、遅いPCでは遅れが無限に積み上がっていた
2. 背景エフェクト（MediaPipe）のモデル読み込みと推論が画面スレッドで動いていた
3. 背景エフェクトの自動画質アップが、重いPCで往復を繰り返していた
4. カメラ映像の圧縮（VP8・ソフトウェア）がCPU不足

## 2. ノイズキャンセル（GTCRN）

### 2-1. 処理の高速化（M4・WASM、1回の推論あたり）

| 方式 | 1回の時間 | 4フレーム分の時間 | 比 |
|---|---|---|---|
| T1（1フレームずつ×4回） | 0.43ms | 1.72ms | 1.00 |
| T2（2フレームずつ×2回） | 0.52ms | 1.04ms | 0.60 |
| **T4（4フレームまとめて1回）** | **0.71ms** | **0.71ms** | **0.41（2.47倍速）** |

- 1回あたりの固定コスト約 0.35ms ＋ 1フレームあたり約 0.09ms。まとめて処理するほど固定コストが減る。出力は T1 と同一。
- T8 は T4 の 1.3倍速だが +64ms 遅れるので見送り（予備）。
- 重いときの段階: 4フレーム中 4 → 2 → 1 フレームだけ推論し、残りはマスクを使い回す（全段階で音質は合格。最初に下げるのは「2フレーム」）。

### 2-2. 遅れが積み上がらない仕組み

- 待ち行列の上限 約300ms（4チャンク）。超えた分は加工せずそのまま流し、最軽量の段階に切り替える。10秒に3回超えたら、ノイズキャンセルをOFFにしてお知らせを出す。
- 音声の経路を画面スレッドから外した（マイク → 処理用のWorker → 再生）。**画面スレッドを3秒止めても声が途切れない**ことを確認（2026-10-13）。
- 再生の溜まりすぎを、無音の部分で少しずつ捨てて戻す処理を追加。

### 2-3. 体感の遅れ（Mac・自分で計測、2026-10-13）

| 状態 | 遅れ |
|---|---|
| 改善前（ノイズキャンセルON） | 約 1秒 |
| 改善後（ノイズキャンセルON） | 約 0.8秒（再生の溜まり 90〜120ms） |
| ノイズキャンセルOFF | 約 0.4秒 |

## 3. 背景エフェクト

### 3-1. 設定ごとの重さ（M4、`/dev/blur-lab`、2026-10-13）

負荷 = 1秒あたりに処理にかかる時間。基準（本番と同じ設定）を 1.00 とした比。

| 設定 | 通常 | GPUの完了を待って計測 | CPUを4倍遅く |
|---|---|---|---|
| 基準（720p・20fps・切り抜き10回/秒） | 26.0ms/秒 (1.00) | 24.2 (1.00) | 32.4 (1.00) |
| 切り抜き 毎フレーム(20回/秒) | 1.54 | 1.52 | 1.18 |
| モデル: 高精細 | 1.15 | 1.30 | 0.95 |
| モデル: 正方形 | 1.00（読み込み 1秒） | 0.94 | — |
| 推論をCPUで | **6.23** | 6.68 | — |
| 解像度 360p | 0.84 | 1.08 | 0.64 |
| カメラ10fps / 切り抜き5回 | **0.42** | 0.52 | 0.34 |

分かったこと:
- 重さはほぼ「切り抜きの回数 × 約1.8〜2.0ms」で決まる。解像度を下げてもほとんど軽くならない。
- 推論をCPUにすると6倍重い（不採用）。正方形モデルは得がない（不採用）。
- 規則（切り抜きはカメラのコマ数の半分以上）の範囲で一番軽いのは「カメラ10fps / 切り抜き5回」で約0.4〜0.5倍。

### 3-2. Workerへの移動（2026-10-13）

| 項目 | 画面スレッドで処理（改善前） | Workerで処理（改善後） |
|---|---|---|
| 1秒あたりの負荷（基準設定） | 26.6ms | 24.8〜29.0ms（**ほぼ同じ 0.93〜1.09倍**） |
| モデル読み込み中の画面スレッドの最大停止 | 59〜118ms | **0ms** |
| モデル切り替え中の画面スレッドの最大停止 | 23〜109ms | **1〜7ms** |
| モデル切り替え時の黒い画面 | **300〜400ms** | **0ms** |

- 途中で試した「切り抜き専用Workerを分ける」方式は、マスクの受け渡しで 13ms/回 かかり 5〜12倍重かった → GPU上の画像のまま渡す方式に変えて 1.08倍 に解決。
- Safari: 背景エフェクトOFF時の黒画面、別タブで映像が止まる問題を修正（Safari 18 の Worker 方式）。

### 4-2. 段階（2026-10-15 時点）

## 6. コーデック

### 6-1. 送る側の圧縮時間（M4、1コマあたり、2026-10-14）

| | VP8 | H.264（MacのChromeはソフトウェア） |
|---|---|---|
| カメラ 320x180 / 640x360 / 1280x720 | 1.4 / 1.6 / 4.2ms | 1.3 / 1.9 / 3.3ms |
| 画面共有 1243x720 | 2.8ms | **8.3ms** |
| 画面共有 1864x1080 | 11.5ms | **31.5ms** |

→ カメラはほぼ同じ。**画面共有は H.264 だと約3倍重い**ので VP8 のまま。

### 6-2. 受け取る側

- Pixel 7: VP8 も H.264 もハードウェアでデコード（5〜8ms / 6〜8ms）→ 差なし。
- iPhone から VP9 を受信した Mac: ハードウェアデコードを試して失敗し、ソフトウェア（libvpx）に戻った。デコード時間は VP8 とほぼ同じ（0.7〜0.8ms）、通信量は約3割減。
- 結論: 遅いPCでデコードを軽くするのは、コーデックより「画素数 × コマ数」を減らす方が効く。

## 11. 画面共有（2026-10-15）

### 11-1. Google Meet の画面共有（M4 の webrtc-internals ダンプ）

| 項目 | Meet | Connect（当時） |
|---|---|---|
| コーデック | **AV1**（libaom・ソフトウェア）、L1T2 | VP8、2層（1080p ＋ 720p 5fps） |
| 解像度 | タブの大きさそのまま 1536x1096（取り込み上限 4K） | 1080p に縮小 |
| 静止中 | 約 2fps・**約17kbps** | — |
| スクロール中 | 20〜27fps・0.4〜0.8Mbps | — |
| 圧縮時間 | 2〜3.5ms/コマ | — |
| エンコーダPSNR | 約 50dB | — |
| 画面の音声 | タブの音をステレオ 64kbps で別送 | なし |

カメラは VP9（640x360〜720p・30fps）。マイクはブラウザの音声処理をすべてOFFにして自前で処理している。

### 11-2. `/dev/share-lab`（M4・自分の画面のスクリーンショット4枚、2306x1600）

| 設定 | スクロール中 | 静止中kbps | 圧縮ms/コマ | デコードms/コマ |
|---|---|---|---|---|
| VP8 1080p 15fps 4M（当時の設定） | 15fps・3.8Mbps | 300 | 9〜11 | 6.6〜7.5 |
| VP8 原寸 15fps 6M | 15fps・4.4〜5.7Mbps | 660〜1700 | 14.5〜17.8 | 7〜10 |
| **AV1 原寸**（Meet式） | 25〜30fps・2.9Mbps | 190〜310 | **8.0〜8.3** | **2.1** |
| VP9 原寸（Meet式） | 14〜15fps（30まで出ず）・1.8Mbps | 30〜180 | 10〜12 | 2.7〜3.5 |
| H.264 1080p | 15fps・2.7〜3.3Mbps | 19〜22 | **26〜38** | 1.0〜1.9 |
| VP8 720p | 13〜15fps・2.4Mbps | 220〜410 | 7.6 | 4.9〜5.8 |

- 見た目（本人の判断）: **AV1 原寸が一番読みやすい**。当時の設定は許容範囲。**720p は「画質が悪い」と断言できる**ので、画面共有の最低ラインは 720p。
- 自動の一致度（PSNR）は、本人のスクリーンショットでは原寸でも約24dBのまま動かず、信頼できなかった（生成した画像では 720p 31dB → 1080p 36dB → 1440p 38dB → 原寸 51〜55dB と正しく並んだ）。原因の調査は中止し、目視で判断した。
- LiveKit は AV1 の画面共有を「L1T3・動画扱い（motion）」に強制する。「画面扱い（detail）」に戻した場合と比べると、静止画の画質は同じ（54.8dB / 54.1dB）、スクロール中の通信量だけ画面扱いが約3割少ない（3.1 / 2.2Mbps）→ まずは LiveKit 標準のまま。
- H.264 は実際の画面だと圧縮が重い（VP8 の約3倍）。以前の通話中の計測（31.5ms）と一致。

### 11-3. 決めたこと（2026-10-15）

- 画面共有は **AV1・画面の大きさのまま（上限 2560x1600）・最大 15fps**、解像度を保ちコマ数を下げる設定。
- AV1 を受け取れない人（Safari・古い iPhone/iPad）がいるときだけ、VP8 1080p も同時に送る（予備コーデックの SIMULCAST 方式。LiveKit 標準の方式だと、1人でもいると全員が VP8 になる）。
- 送る側が重いとき（自動で軽くする仕組みの段階）: カメラの段階 → 受信3 → **AV1 → VP8 1080p** → カメラOFF → **VP8 720p（最低ライン）**。VP8 に落ちた端末は、14日間は最初から VP8 で共有する。
- 受け取る側が重いとき: 画面共有は**コマ数だけ**半分にする（解像度＝文字の読みやすさは変えない）。

### 11-4. 本番で AV1 にしたら重くなった（2026-10-16、M4、診断 20261016-NEN4AB）

- 普段の操作（スクロール・クリックしてページ移動）をしながら約60秒共有。取り込みはほぼずっと 11〜15fps（画面が動き続けていた）。
- AV1 の圧縮が **12〜40ms/コマ、ときどき 95〜400ms**（実験ページでは 8〜10ms）。それでも圧縮は「CPU不足」を一度も報告しなかった。
- 同じPCのノイズキャンセルが 5ms → 30〜230ms/チャンクに悪化し、**共有中ずっと最軽量の設定に張り付き**、音声の途切れも増えた。画面スレッドの長いタスクも 100〜750ms/秒。
- **自動で軽くする仕組みは共有中に一度も動かなかった**: Connect のタブが共有中は裏に隠れていて、「隠れたタブの数字は判断しない」作りだったため（共有中は毎回そうなる）。

直したこと:
- 隠れたタブでも、音声・圧縮・画面共有の圧縮の重さでは判断する（画面スレッド・背景エフェクト・受信映像はブラウザが隠れたタブで遅くするので除外）。この日の記録を再生すると、共有開始から 6〜12秒で動き出す。
- 画面共有の圧縮の重さを直接測る基準を追加（1コアの40%以上、または1コマ60ms以上）。AV1 の共有がそれに当たるときは、カメラより先に VP8 へ切り替える。切り替えのあとは必ず15秒待ってから次を判断する。
- 画面共有の初期設定を **VP8（1080p・解像度を保つ）に戻した**。AV1 は「通話の診断」の切り替えから選べる（画面共有のみ）。
- 自分の共有画面は、通話画面でも PiP でも「画面を共有しています」の表示に置き換え（合わせ鏡を防ぐ）。ボタンでプレビューも出せる。共有する画面の候補から Connect のタブ自体を外した。

実験ページと本番の差の仮説（未確認）: 実験は大半が静止した画像で、スクロールも同じ画像を平行移動するだけ（AV1 が最も得意な条件）。本番はページの読み込みや表示の変化で毎コマ新しい内容が出る。さらに LiveKit が AV1 の画面共有を「動画扱い」に強制していて、Meet（画面扱い・L1T2）と設定が違う。共有中はタブが裏に回り、ブラウザが処理の優先度を下げる影響もありうる。→ 実験ページの「本番の候補だけ」を、実際に動かしている画面で測って確かめる。
